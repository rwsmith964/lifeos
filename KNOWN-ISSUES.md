## Fixed and verified live this pass (D-058 — calendar event add/edit 500 in production)

`/calendar/new` and `/calendar/[id]/edit` returned a hard HTTP 500 on every request in production (React error #441 — "error occurred in the Server Components render"), even though `pnpm typecheck`/`pnpm lint`/`pnpm test`/`pnpm build` all passed cleanly. ## Found during D-059 live verification — pre-existing shared component quirk, not a D-059 bug

The `ConfirmDeleteButton` shared component (used by the Trip Ideas delete control, and by the pre-existing activity-deactivate button) toggles into a "Confirm delete / Cancel" state on first click. During live verification, a slow or hesitant second click sometimes landed after the confirm state had already auto-reverted back to normal — the click then silently fell through to whatever control occupies that same screen position afterward (e.g. an adjacent edit-pencil link) instead of doing nothing or showing feedback. Not a data-loss risk (worst case is navigating to the wrong page, not an unintended delete), but worth a UX pass at some point: either extend the auto-revert timeout, or make the confirm state require an explicit outside click/Escape to dismiss instead of timing out.
